# NB Development Defaults — Router

- Execute implementation requests using the actual repository and observed tool results. Read `CHARTER.md`, `CHITTY.md`, `AGENTS.md` and discover existing ChittyRegistry capabilities before inventing a service or schema.
- Keep GitHub issues, commits, checks and PRs as canonical development evidence. Do not claim unexecuted tests or unverified deployment.
- Select a focused sibling skill: `recursive-development-orchestrator` for sustained loops, `chittyos-mcp-routing` for connected capabilities, `development-governance` for canonical authority, `development-work-continuity` for issue/PR state, `development-security-gates` for authorization/release risk, `ci-repair-loop`, `pr-finalizer`, `deployment-verifier`, `repository-hygiene`, `manifest-forge-publisher` for cross-runtime skill publishing, or `chittyos-integration-auditor` for their named purposes.
- Existing authoritative skills remain authoritative: `capability-governor`, `chittyos-compliance`, `mcp-gateway-reconciler`, and `chittypro-legal-design`/evidence skills when applicable. Discover and invoke them where available; do not copy their rules into competing sources.
- Reuse ChittyAuth, ChittyConnect, ChittyID, ChittyCert, ChittySecrets, existing Cloudflare CI and existing gateways. Avoid paid GitHub Actions and new staging Workers unless expressly approved.
- Never create recurring automations or background agents by inference. A commit or PR is not a reason to stop an active development loop.
